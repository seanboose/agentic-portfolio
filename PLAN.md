# Portfolio Website — Plan

## Stack
- **Frontend**: Vite + React + TypeScript (CRA is deprecated/unmaintained as of 2026; Vite is the React team's recommended replacement)
- **Backend**: Node/Express
- **Data**: static JSON file, no database
- **Deployment**: unified — Express serves both the API and the built React app from a single process. Chosen over split hosting (separate static host + API host) because: low-traffic portfolio site doesn't need independent scaling of FE/BE; avoids CORS + dual-deploy-pipeline complexity; simpler mental model for someone new to this pattern (user has only done split hosting before). Deploying to **Render** (user already deploys their existing portfolio there).

### Build pipeline (shared → server/client)

`shared` is consumed by both `client` and `server` as a compiled package (its `package.json` `main`/`types` point at `dist/`, not `src/`) — so it must build *before* either consumer, in dev and in prod alike.

```
shared/package.json
  "main": "dist/project.js", "types": "dist/project.d.ts"
  scripts: { "dev": "tsc --watch --preserveWatchOutput", "build": "tsc" }

server/package.json
  scripts: { "dev": "tsx watch src/index.ts", "build": "tsc", "start": "node dist/index.js" }
  (plain `node` in prod — no tsx/ts-node runtime dependency in production)

client/package.json
  scripts: { "dev": "vite", "build": "vite build" }
```

Root scripts:
```jsonc
{
  "workspaces": ["shared", "server", "client"],
  "scripts": {
    // fast path: after a fresh `npm install`, shared/dist already exists
    // before anyone runs `dev` or `build`
    "postinstall": "npm run build -w shared",
    // safety net: guarantees shared/dist exists regardless of *why* it might be
    // missing (fresh clone, `git clean`, manual rm -rf of dist) — not just the
    // fresh-install case postinstall covers. Runs once, then the three concurrent
    // processes start; shared's own tsc --watch takes over incremental rebuilds
    // from there. The extra build is a near-zero-cost redundant compile on the
    // common path (shared is tiny), traded for eliminating an entire class of
    // "works on my machine" races.
    "dev": "npm run build -w shared && concurrently \"npm run dev -w shared\" \"npm run dev -w server\" \"npm run dev -w client\"",
    // order matters: shared has no deps; server and client both require shared/dist to exist
    // (server's own tsc typechecks against it; client's Vite build resolves imports through it)
    "build": "npm run build -w shared && npm run build -w server && npm run build -w client",
    "start": "npm run start -w server"
  }
}
```

`shared/dist` and `server/dist` are gitignored (generated output, not checked in) — nothing outside this repo consumes them without also being able to rebuild them, so checking them in would just risk `dist` drifting stale relative to `src`. On Render, `npm install && npm run build` (the build command) covers this the same way; `postinstall` + `dev`'s own build-first step handle the local/dev equivalent.

## Dev-time FE↔BE communication

Two dev servers: Express on e.g. `:4000`, Vite dev server on `:5173`. Vite's `server.proxy` config forwards `/api/*` and `/images/*` to `:4000`. Client code always uses relative paths (`fetch('/api/projects')`) — identical in dev and prod, no CORS config, no env-var branching for API base URL.

## Production serving

Single Express process:
1. `client/dist` gets built via `vite build`
2. Express serves it as static files, plus `/api/*` routes, plus `/images/*` static assets
3. Catch-all route serves `index.html` for any unmatched path, so React Router can handle client-side routes on refresh/direct navigation

### Express route order (critical — must be in this order)
```ts
const app = express();

// 1. API routes first — most specific, must not be shadowed
app.use('/api/projects', projectsRouter);

// 2. Static assets — express.static calls next() on a miss, so safe before the catch-all
app.use('/images', express.static(path.join(__dirname, '../public/images')));
app.use(express.static(path.join(__dirname, '../../client/dist')));  // also serves index.html at "/"

// 3. SPA fallback last — anything unmatched falls through to index.html;
//    React Router reads the URL client-side and renders the right page.
//    (This does NOT mean refreshing always shows the homepage — the URL bar
//    is unchanged, so React Router renders the correct route once it mounts.)
app.get('*', (req, res) => {
  res.sendFile(path.join(__dirname, '../../client/dist/index.html'));
});
```

## Data schema (Zod, shared package)

Runtime-validated (not just compile-time typed), TypeScript type inferred from the Zod schema so they can never drift apart. Discriminated union on `type` so software-only fields (`liveUrl`/`repoUrl`) are inaccessible on art projects at the type level. Includes a `.superRefine()` check enforcing unique `id`s across the array (ids double as URL slugs — duplicates would cause silent, hard-to-debug lookup bugs), which fails the whole parse with a specific "duplicate id(s): ..." message at server startup.

```ts
// shared/src/project.ts
import { z } from "zod";

const BaseProjectSchema = z.object({
  id: z.string(),
  title: z.string(),
  tagline: z.string(),
  tags: z.array(z.string()),
  date: z.string().regex(/^\d{4}-\d{2}$/),   // "YYYY-MM"
  featured: z.boolean(),
  thumbnail: z.string(),
  images: z.array(z.string()),
  body: z.string(),                           // markdown
});

const SoftwareProjectSchema = BaseProjectSchema.extend({
  type: z.literal("software"),
  liveUrl: z.string().url().optional(),
  repoUrl: z.string().url().optional(),
});

const ArtProjectSchema = BaseProjectSchema.extend({
  type: z.literal("art"),
});

export const ProjectSchema = z.discriminatedUnion("type", [
  SoftwareProjectSchema,
  ArtProjectSchema,
]);

export const ProjectsSchema = z
  .array(ProjectSchema)
  .superRefine((projects, ctx) => {
    const seen = new Set<string>();
    const duplicates = new Set<string>();
    for (const p of projects) {
      if (seen.has(p.id)) duplicates.add(p.id);
      seen.add(p.id);
    }
    if (duplicates.size > 0) {
      ctx.addIssue({
        code: z.ZodIssueCode.custom,
        message: `Duplicate project id(s): ${[...duplicates].join(", ")}`,
      });
    }
  });

export type Project = z.infer<typeof ProjectSchema>;
```

### Startup validation (not per-request)

`projects.json` is static file content, not user input, so it's validated once at server boot rather than on every request. A schema violation crashes the server immediately with a specific Zod error (which field/index/check failed) instead of surfacing later as a confusing bug or bad API response.

```ts
// server/src/data/loadProjects.ts
import { ProjectsSchema, type Project } from "@portfolio/shared";
import raw from "./projects.json";

export const projects: Project[] = ProjectsSchema.parse(raw);
```

Route handlers in `routes/projects.ts` serve from this already-validated in-memory array — no re-parsing per request.

## Project types: software vs. art

Site covers both software projects and art (e.g. paintings), sharing one schema/collection/route set (not split into separate collections) — the `type` discriminant is enough since most fields (title, images, body, tags, date) are medium-agnostic. `tags` vocabulary differs by convention (tech stack vs. medium/style) but is the same field. Only `liveUrl`/`repoUrl` are software-specific, enforced via the discriminated union.

Home page shows one unified grid with client-side All/Software/Art tabs (not separate `/software` and `/art` routes) — filtering happens in the browser since the dataset is small.

## API

```
GET /api/projects        -> full array of all projects
GET /api/projects/:id    -> single project by slug, 404 if not found
```

No query-param filtering (e.g. `?featured=true`) — featured/type filtering happens client-side since the full dataset is small enough to fetch once.

## Images

- **Format**: WebP. Hand-converted via Squoosh.app or editor export — **reminder: user needs to convert existing/new assets to WebP when adding real project images, since this is a new step in their usual export habit.**
- **Sizing**: rough manual targets — thumbnails ~600px wide, gallery/detail images ~1600px wide, resized before export. (Display size in the UI is controlled by CSS regardless of source resolution; resizing before export is purely about not shipping unnecessarily large downloads.)
- **Storage**: single copy only, no separate source/generated pipeline — `server/public/images/<project-slug>/*.webp`, served via `express.static`. No sharp/build-step image tooling.

## Frontend data fetching

**React Query** (`@tanstack/react-query`), not hand-rolled `useEffect`/`useState` — user has React Query experience and prefers to avoid `useEffect` where possible. Gives caching + loading/error states for free.

Dependencies to add: `@tanstack/react-query`, `react-router-dom`, `react-markdown` (renders the `body` markdown field), `zod` (in `shared` only).

## Verification step (required before considering scaffolding "done")

Dev mode and the production build are genuinely different code paths (Vite dev server + proxy vs. Express serving static `dist/`; `tsx`'s on-the-fly transpile vs. `tsc` compilation, which catches different classes of errors) — passing one is not evidence the other works. Both must be verified end-to-end in a browser before scaffolding is considered done. Passing typecheck/build alone is not sufficient either.

**Dev mode:**
1. Run `npm run dev` from a clean state (confirms the `postinstall`/build-first race fix actually works, not just the happy path)
2. In a browser at the Vite dev URL, confirm the homepage loads and renders project cards
3. Confirm card data is genuinely coming from `GET /api/projects` through the Vite proxy (not hardcoded) — e.g. via Network tab, or by temporarily editing `projects.json` and confirming the change reflects
4. No console errors on load

**Production build:**
1. Run `npm run build` from a clean state, confirm it completes with no errors (this exercises `shared`'s `tsc`, `server`'s `tsc`, and `vite build` together, in the real dependency order)
2. Run `npm run start`, hit the single Express port in a browser
3. Confirm the homepage loads and renders project cards served from the compiled Express app (static `client/dist` + `/api/projects` from compiled `server/dist`)
4. Confirm a client-side route survives a hard refresh (e.g. navigate to a project detail page, refresh, confirm it still renders the detail page and not a 404 or blank homepage) — this specifically exercises the SPA-fallback catch-all route
5. No console errors on load

## Styling

CSS Modules, hand-written (`*.module.css` per component), no framework/dependency — enough to make the grid/cards/detail page legible during scaffolding and verification, not a final design. Easy to replace once a real visual direction exists. Vite supports CSS Modules out of the box, no extra config needed.

## Lint / format

Single ESLint + Prettier config at the repo root, covering all three workspaces (`client`-specific rules like React hooks/JSX scoped via ESLint file-pattern overrides in the same root config, not a separate config file). `npm run lint` / `npm run format` as root scripts.

No git hook (no husky/lint-staged) — solo project, not needed to prevent bypassing checks. No committed IDE config either — instead, `npm run format` and `npm run lint:fix` are plain, self-contained scripts the user points their editor at directly (e.g. WebStorm's "run npm script on save" / File Watchers), so format-on-save is a per-developer editor setting, not something checked into the repo.

## Environment variables

No secrets exist yet (no DB, no API keys, no auth) — just port config. Pattern is set up now so it's ready the moment a real secret shows up, without needing to re-architect env handling later.

```
portfolio/
  .env                       # committed, non-secret, shared across dev/prod defaults — e.g. PORT=4000
  .env.development.local     # gitignored, dev-only secrets — empty/placeholder for now
  .env.example                # committed template documenting the shape of .local, no real values
```

- `server` depends on `dotenv`; `server/src/index.ts` calls `import 'dotenv/config'` early (dev only in effect — in prod there's no `.env.development.local` file to load, and Render injects real env vars, including `PORT`, directly into `process.env`)
- `.gitignore` excludes `*.local` env files but **not** `.env` or `.env.example`
- Production secrets: added manually by the user directly in Render's dashboard (environment variables section) when a real secret exists — not part of scaffolding, nothing to automate here

## Testing

Two layers, matching the two verification passes already run by hand during scaffolding:

- **Vitest** — unit tests for pure logic, colocated with source. Currently just `shared/src/project.test.ts`: valid software/art projects parse, duplicate `id`s are rejected (mirrors the manual crash-test done during scaffolding), wrong `type` literal is rejected. `shared/package.json` gets a `test` script + `vitest` devDependency; root gets `"test": "npm run test -w shared"`.
- **Playwright** — end-to-end, lives in its own `e2e/` package at the root (tests the seam between client and server, doesn't belong to either). Runs against the **production build**, not dev mode — same code path Render serves, and it's what most of scaffolding's manual verification already exercised (SPA-fallback route order, static serving). `e2e/playwright.config.ts` uses the `webServer` option to run `npm run build && npm run start` and wait on `http://localhost:4000` before tests execute (`reuseExistingServer: !process.env.CI` so local runs can reuse an already-running server).

```
portfolio/
  shared/
    src/
      project.ts
      project.test.ts        # vitest
    vitest.config.ts
  e2e/
    playwright.config.ts
    tests/
      home.spec.ts            # cards render from API, filter tabs, software/art link gating
      project-detail.spec.ts  # detail page content, hard-refresh survives (SPA fallback)
    package.json
```

Root scripts add `"test": "npm run test -w shared"` and `"test:e2e": "npm run test:e2e -w e2e"`.

**Browser binary install is a manual, documented, per-machine step** — not wired into `postinstall`. Reasoning: the Playwright browser cache lives outside the project (`~/.cache/ms-playwright`, keyed by Playwright version) so it's a per-machine/per-version concern, not a per-`npm install` one; it's a large (~300MB) download not everyone needs immediately; and `--with-deps` (system libraries Chromium needs to actually *launch*, not just download) can require sudo on a machine that doesn't already have them, which shouldn't happen silently inside `npm install`. Documented in a new root `README.md`:

```
## Getting started
npm install

## Running e2e tests (one-time per machine)
npm run test:e2e:setup -w e2e
# if the browser fails to launch on a fresh machine, try:
# npx playwright install chromium --with-deps
```
